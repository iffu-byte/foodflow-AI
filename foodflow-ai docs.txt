## Project: FoodFlow AI
### Transform FoodFlow AI into a Zomato-like food ordering, restaurant management, rider delivery and real-time operations platform.

Act as a Senior Full-Stack Architect, Product Engineer, Backend Developer, Frontend Developer, Database Architect, Real-Time Systems Engineer and UI/UX Designer.

You are working on an existing project called **FoodFlow AI – Intelligent Food Delivery Prediction, Tracking and Optimization Platform**.

The existing project already has an **Admin Console**. Do not rebuild or replace it. First inspect the complete repository, understand its architecture, identify existing functionality and extend it.

Your responsibility is to transform the current application into a fully connected food delivery marketplace with:

1. Customer Dashboard
2. Rider Dashboard
3. Existing Admin Console integration
4. Restaurant Order Management integration or a minimal restaurant operations interface if one does not exist
5. Centralized Backend
6. Real-Time Communication
7. AI-Based Delivery ETA
8. Intelligent Rider Assignment
9. Live Order Tracking

The final result must behave like a real food delivery platform, following familiar marketplace functionality found in applications such as Zomato and Swiggy, while retaining FoodFlow AI's own identity and AI capabilities.

Do not just create attractive static dashboards. Every major interface must be connected to working backend APIs, PostgreSQL database operations, authentication, authorization, and real-time events.

# PHASE 8: COMPLETE ORDER LIFECYCLE

This is the central workflow of FoodFlow.

Implement it as a backend-controlled state machine.

## Stage 1 – Order Placement

Customer selects food and completes checkout.

Backend:

1. Validate customer authentication.
2. Validate restaurant.
3. Validate menu item availability.
4. Recalculate order amount.
5. Create order.
6. Create order items.
7. Create initial order event.
8. Record payment method and appropriate payment status.
9. Commit the database transaction.
10. Publish order-created event.

Customer sees:

"Your order has been placed successfully."

Admin Console sees:

"New Order Received."

Restaurant dashboard sees:

"New Incoming Order."

## Stage 2 – Restaurant Confirmation

Restaurant receives a new order.

Restaurant can accept or reject.

On acceptance:

- Change restaurant/order status.
- Record confirmation.
- Record preparation estimate.
- Inform customer.
- Update Admin Console.
- Trigger initial delivery planning.

On rejection:

- Record reason.
- Notify customer.
- Apply the configured refund/cancellation rules.
- Release any reserved resources.

## Stage 3 – Food Preparation

Restaurant marks:

PREPARING

Backend records preparation state and estimates readiness.

Customer sees:

"Your food is being prepared."

Admin sees:

"Restaurant Preparing Order."

ETA engine calculates expected delivery time.

## Stage 4 – Rider Discovery

Dispatch engine searches for eligible riders.

Check:

- Rider online status.
- Verification status.
- Location freshness.
- Pickup distance.
- Existing active delivery count.
- Configured delivery capacity.
- Vehicle suitability.
- Current assignment availability.

Select an eligible candidate.

Do not assign riders based on distance alone.

Do not assign a rider with an invalid or stale location unless the system explicitly permits an approved fallback.

## Stage 5 – Rider Offer

Create a delivery offer.

Send it to the selected rider using an authenticated real-time event.

Rider receives:

"New Delivery Available."

Rider accepts or rejects.

If accepted:

- Use a transaction to claim the assignment.
- Verify no other rider has already claimed it.
- Mark rider assigned.
- Update order's rider relationship.
- Publish rider-assigned event.

If rejected or expired:

- Mark that offer declined/expired.
- Try the next eligible candidate.
- Enforce a maximum retry count.
- Notify Admin if automated assignment fails.

## Stage 6 – Food Ready

Restaurant marks:

READY_FOR_PICKUP

Customer sees the update.

Assigned rider sees pickup-ready information.

If no rider exists, dispatch continues or Admin can manually assign one.

## Stage 7 – Rider Pickup

Rider arrives at the restaurant.

Rider selects:

ARRIVED_AT_RESTAURANT

After required verification, rider marks:

PICKED_UP

Backend:

- Validates the assignment.
- Updates delivery progress.
- Records pickup time.
- Publishes the pickup event.
- Recalculates ETA.
- Notifies customer and Admin.

Customer sees:

"Your order has been picked up!"

## Stage 8 – Delivery in Progress

Rider selects:

ON_THE_WAY

Rider location is updated through a secure API or WebSocket.

Backend broadcasts authorized location updates.

Customer tracking page displays the rider moving along the route.

Calculate remaining ETA.

Do not send location updates indefinitely when the rider is offline or has completed the delivery.

## Stage 9 – Delivery Completion

Rider reaches destination.

Optional OTP verification.

Rider selects:

DELIVERED

Backend:

1. Validates assigned rider.
2. Validates that pickup happened.
3. Validates delivery completion requirements.
4. Updates order status.
5. Records actual delivery time.
6. Closes delivery assignment.
7. Updates rider availability.
8. Creates earnings entry.
9. Publishes order-delivered event.
10. Updates customer history.
11. Updates Admin Console analytics.
12. Enables customer review.

Customer sees:

"Enjoy your meal! Your order has been delivered."

# PHASE 10: INTELLIGENT RIDER DISPATCH ENGINE

Build a separate backend Dispatch Service.

It should not exist only in frontend logic.

## Rider eligibility

Only consider riders that satisfy:

- Account active.
- Verification approved.
- Online.
- Location sufficiently recent.
- Not currently unavailable.
- Under configured capacity.
- Vehicle appropriate for delivery.

## Rider scoring

Implement a transparent weighted scoring system.

Example:

SCORE = 0.55 * NORMALIZED_PICKUP_TIME
      + 0.30 * NORMALIZED_ACTIVE_WORKLOAD
      + 0.15 * VEHICLE_SUITABILITY_PENALTY

Lowest eligible score wins.

Keep weights configurable.

Use road ETA where available; otherwise use clearly identified distance-based approximation.

Record why the rider was selected.

For simultaneous orders, use transaction locks, uniqueness constraints or an atomic claim operation.

Prevent race conditions where two customers' orders get assigned to the same unavailable rider.

## Assignment retry strategy

- Attempt first eligible rider.
- If rejected, offer to next rider.
- Handle timeout.
- Limit repeated offers.
- Prevent duplicate assignments.
- Log all decisions.
- Escalate to Admin if no eligible rider is found.

Admin should be able to manually override assignment where authorized.

# PHASE 11: AI DELIVERY ETA INTEGRATION

Preserve the existing FoodFlow AI machine-learning implementation if present.

Inspect existing models, feature preprocessing, training data and prediction APIs before modifying anything.

The ETA engine should account for:

- Restaurant preparation time.
- Restaurant workload.
- Road distance.
- Route duration.
- Traffic condition where genuinely available.
- Time of day.
- Day of week.
- Weather where available.
- Rider pickup distance.
- Remaining delivery distance.
- Model version.
- Uncertainty range.

Use the actual trained ML model when available.

If the trained model is unavailable or input data is incomplete, use a documented fallback estimation formula.

Do not generate arbitrary random predictions.

Do not claim live traffic when only static route information is available.

Separate these calculations:

1. Preparation estimate.
2. Rider arrival at restaurant estimate.
3. Pickup wait estimate.
4. Restaurant-to-customer travel estimate.
5. Final delivery ETA.

Display an ETA range using validation residuals or another defensible uncertainty method.

Each prediction must store:

- Predicted ETA.
- Lower bound.
- Upper bound.
- Prediction source.
- Model version.
- Prediction timestamp.
- Actual delivery time when available.

## Predictive delay detection

When updated conditions cause estimated delivery time to exceed the promised window:

- Create a delay event.
- Recalculate ETA.
- Evaluate recovery options.
- Notify the customer.
- Show the delay in Admin.
- Record the recovery recommendation.

If the rider has not picked up the food, reassignment may be recommended if it genuinely improves the expected delivery outcome.

After pickup, avoid automatic rider transfer in the MVP.

Explain why the ETA changed.
